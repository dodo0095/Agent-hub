# 派工 prompt 模板 — 五種常見任務型態

> **版本**: v1.0（2026-07-06，Fable 5 制度建設 session）
> **用法**: 指揮官派工時**整段抄走**對應模板，填掉所有 `【…】` 填空後作為 `Agent` 工具的 `prompt`。填不出「驗收條件」= 這個任務還沒想清楚，不准派（`model-dispatch.md` 第 3 節）。
> **通用規則**: `subagent_type` 與 `model` 按 `model-dispatch.md` 第 4 節對照表選，一律顯式指定。
> **共用段要真的展開**: 模板尾的「＋環境提示段」「＋回報合約段」是動作指令，不是裝飾——把下方共用段**原文整段**貼進最終 prompt。送出前機械檢查：prompt 內找得到「環境：Windows 11」和「回報格式（嚴格遵守）」兩個字串，找不到 = 忘了貼，不准送。

---

## 共用段（每份模板已內建，不要刪）

**環境提示段**（原樣保留在 prompt 裡）：

```
環境：Windows 11 + Git Bash。禁用 cmd.exe / PowerShell 語法 / findstr / python3（用 python）。
路徑含空格（ALL PROJECT），一律加雙引號。工作目錄與分支先用 pwd 和 git branch --show-current 確認。
不確定的事去讀原始碼或執行指令取證，禁止編造；沒驗證的結論標「未驗證」。
```

**回報合約段**（原樣保留在 prompt 裡）：

```
回報格式（嚴格遵守）：
1. 結論：≤ 10 行，關鍵主張各附 檔案:行號
2. 長產物寫入檔案，只回傳路徑
3. 實際執行過的驗證指令＋輸出摘要（≤ 5 行）
4. 未驗證清單：沒驗過的一律列在這裡，不准混進結論
```

## 模板 1：搜尋 / 盤點（`Explore` + `sonnet`）

> **派工前自問**：關鍵字精確已知、一次 Grep 就解得了 → **不派**，指揮官自己 grep（`model-dispatch.md` 第 1 節）。本模板用於要換多種關鍵字、或要理解語意才找得齊的搜尋。

```
【目標】找出：【要找什麼，例：所有讀取 cost 資料的程式碼路徑】
【動機】因為：【找到後要拿來做什麼，例：下一步要改 cost 寫入時機，需要完整影響面】
【範圍】只搜 【目錄/檔案類型】；已知線索：【關鍵字、已知的一個實例、命名慣例】
【語意界定】要找的是【寫入者/讀取者/定義處/呼叫處——選一個】；只出現檔名字串但不做該動作的，列入「相關但不符合」另計

【驗收條件】
- 列出全部符合項，各附 檔案:行號 與一行說明「它做什麼」
- 明確回答「除了以上沒有其他了」或「以下位置沒搜（原因）」
- 不要貼大段程式碼，每項引文 ≤ 3 行

＋環境提示段
＋回報合約段
```

## 模板 2：實作（`general-purpose` + `sonnet`）

```
【目標】實作：【功能一句話】
【動機】【為什麼要做，使用者場景】
【規格】輸入：【…】 輸出：【…】 邊界情況：【至少列 2 個】
【約束】遵守 .knowledge/coding-standards.md；改 IPC 必須四方同步（ipc.ts/preload.ts/useIpc.ts/env.d.ts）；
        改 electron/** 後必須 npm run build；不得動 【明確列出禁區檔案/功能】
【模式參考】照 【檔案:行號】 的既有寫法

【驗收條件】
- 【具體行為斷言，例：呼叫 X 後 DB 的 Y 欄位變成 Z】
- npx vitest run 【相關測試檔】 全綠；npm run lint 與 typecheck 乾淨
- node scripts/preflight.cjs 通過並附輸出
- 新增行為有對應新測試，不只是沿用舊測試

＋環境提示段
＋回報合約段
```

## 模板 3：重構（`general-purpose` + `sonnet`）

```
【目標】重構：【範圍】，從【現狀】改成【目標形態】
【動機】【為什麼值得動它】
【不變式】重構 = 行為不變。以下可觀察行為必須完全一致：【列出，例：CLI 輸出、API 回傳、DB 寫入】
【約束】禁止順手加功能或修「看不順眼」的別處；發現真 bug 不要修，記下來回報

【驗收條件】
- 改動前先跑 【測試指令】 記錄基準（全綠才准動工；有紅先停手回報）
- 改動後同一指令全綠，測試本身未被修改（若必須改測試，逐條說明為什麼）
- git diff --stat 的範圍不超出【約定範圍】
- node scripts/preflight.cjs 通過並附輸出

＋環境提示段
＋回報合約段
```

## 模板 4：研究 / 查證（`general-purpose` + `sonnet`；查 Claude Code/API 用法改派 `claude-code-guide`）

```
【目標】回答：【具體問題，可判定真假的形式】
【動機】【這個答案會決定什麼】
【來源優先序】1. 本 repo 原始碼實查 2. 官方文件 3. 其他網路來源（標明可信度）
【禁止】憑訓練記憶回答版本號、API 簽名、設定格式這類會過時的事實

【驗收條件】
- 每個結論附來源（檔案:行號 或 URL）；來源之間矛盾時列出矛盾，不要自行折衷
- 區分三類：已證實 / 高信度推斷（附推理）/ 查不到（明說查不到，不編造）
- 若答案是「做法」，附一個最小可驗證例子

＋環境提示段
＋回報合約段
```

## 模板 5：審查 / 驗收（`general-purpose`；常規 `sonnet`，高風險 `opus`——判定見 judgment-rubrics 判準 1）

```
【目標】以 fresh context 審查：【產物路徑 / git diff 範圍】
【你的身分】你沒有參與實作，不知道作者意圖，只依下列標準判定。這是刻意的：不要向作者「善意解讀」
【驗收標準】（逐條判定 通過/不通過/無法判定，附 檔案:行號 證據）
- 【從派工時的驗收條件原樣抄過來】
- 【產物類型對應的品質底線，查 judgment-rubrics 判準 5 的表】
【審查動作】文件：read-back——逐條回答「標準 X 在檔案哪一行被滿足」；
           程式碼：實際執行 【測試/preflight 指令】，不接受作者聲稱的結果

【驗收條件（對你這個審查者）】
- 每條標準都有明確判定與證據，禁止「大致沒問題」
- 「無法判定」是合法結論，附無法判定的原因
- 發現標準之外的嚴重問題（會刪資料、會壞基準線）額外列出；小毛病不擴大範圍

＋環境提示段
＋回報合約段
```

## 派工後（指揮官檢查表）

- [ ] 回報是否符合回報合約？不符合 → 退回要求補格式，不要自己去讀原始檔補位
- [ ] 抽查 1-2 個 `檔案:行號` 引用是否屬實（防編造；抽查用 Read 指定行號，成本低）
- [ ] 失敗 → 查 `model-dispatch.md` 第 6 節升降級路徑，換 fresh subagent，禁止在原 subagent 上加提示重試超過 1 次
- [ ] 「未驗證清單」有內容 → 決定：補驗（派驗收模板）或明示接受風險，不能無視
