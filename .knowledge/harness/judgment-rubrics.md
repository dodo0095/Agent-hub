# 判斷力外化 — 五個判準的 rubric 與 checklist

> **版本**: v1.0（2026-07-06，Fable 5 制度建設 session）
> **讀者**: 任何等級的模型。每條判準 = 觸發訊號（可觀察，不靠自覺）＋檢查表＋一個正例＋一個反例。
> **與決策表的分工**: `decision-tables.md` 是「查表即執行」的 if-then；本文件補的是「**怎麼發現現在該查表了**」＋決策表沒覆蓋的判斷（升級模型、換路訊號）。兩邊規則衝突時以決策表為準並回報（見 `maintenance-protocol.md`）。

---

## 判準 1：何時該升級模型（在失敗之前就認出來）

`model-dispatch.md` 第 6 節是**失敗後**的機械升級梯。本判準是**派工前**就直接派 `opus` 的識別法。

**觸發訊號**（任一成立 → 直接用 `opus`，不要先用 `sonnet` 試）：
- [ ] 任務要在 ≥ 2 個互相衝突的約束之間取捨（如：相容性 vs 簡潔、速度 vs 正確性），且沒有規範文件直接給答案（「確認沒有」的操作定義：查 CLAUDE.md 按情境路由表指到的那**一份**文件，一次查閱沒有直接答案即成立；不需要為此掃全 repo）
- [ ] 動作不可逆或高代價回滾（刪資料、改 DB schema、動 production、改制度檔案）
- [ ] 驗收條件寫不出可機械檢查的版本（= 品味成分高）
- [ ] 已觸發決策表表 2 的除錯熔斷（同症狀第 3 次）
- [ ] 需要提出新設計，而不是照既有模式做

**反向訊號**（都不成立 → 用 `sonnet`/`haiku`，用 `opus` 是浪費）：任務有明確驗收條件＋既有模式可循＋錯了可以重來。

- **正例**: 「cost 累計數字跟 JSONL 對不上，已修兩次沒好」→ 符合熔斷訊號，直接派 `opus` 帶完整失敗軌跡做端到端分析。
- **反例**: 「把 12 個測試檔的 import 路徑從 a/ 改成 b/」→ 有明確模式、可機械驗收，派 `opus` 是燒錢；`haiku` 批次做＋`sonnet` 驗收即可。

## 判準 2：何時算真的完成

**觸發訊號**：你正要打出「完成」「修好了」「應該可以了」「done」這類字眼——**打字前**先過這張表。

**檢查表**：
- [ ] 決策表**表 1** 查過了，我的證據等級對得上變更類型（不是「有證據」，是「有**對級**的證據」）
- [ ] `node scripts/preflight.cjs` 跑過且輸出貼得出來
- [ ] 派工時寫的驗收條件逐條打勾，沒有一條是「我覺得滿足了」
- [ ] 假修復三問（決策表表 2 末尾）答完：用戶跑的版本含這個 fix？綠是測到本體還是 mock？權威資料源現在長什麼樣？
- [ ] 沒驗的部分明確列成「未驗證：…」，而不是不提

- **正例**: 修 cost 統計後，query production DB 貼出修復前後的數字對比＋preflight 輸出，另列「未驗證：跨月彙總場景」。
- **反例**: PM-011——單元測試綠就宣告 cost 修復完成，實際 app 跑的是舊 bundle，20 天後才發現。單測綠 ≠ 資料真的變了。

## 判準 3：何時該停下來問使用者

決策表**表 3** 已列必停情境（刪除/覆蓋、規範矛盾、偏離 dev-plan）。本判準補「表 3 沒列到時怎麼判」＋怎麼問。

**該問的訊號**（任一成立 → 問）：
- [ ] 錯了的代價由使用者承擔且難回復（花錢、對外發送、刪東西、動制度）
- [ ] 兩個方案都合理，但選擇會被長期沿用（命名慣例、目錄結構、依賴選型）
- [ ] 我發現自己在「猜使用者想要什麼」而不是「猜技術上怎麼做」——技術可以查真相來源，意圖沒有真相來源可查
- [ ] 品味判斷且結果會示人（文案語氣、UI 觀感）——先出 2-3 個候選再問，不要空手問

**不該問的訊號**（成立 → 自己決定，記下假設）：規範已覆蓋／存在慣例預設／錯了可低成本重來。問這種問題是把判斷成本轉嫁給使用者。

**怎麼問**：攢批一次問（≤ 5 題），每題附推薦選項＋一句理由。問完就不再停。

- **正例**: 「制度檔案要放 Agent-hub repo 還是工作區根目錄？兩者都合理但影響 14 個專案的引用路徑」→ 該問（長期沿用＋使用者承擔）。
- **反例**: 「這個內部函數要叫 `parseLog` 還是 `readLog`？」→ 不該問。查 coding-standards，沒有就選一個記下假設。

## 判準 4：什麼訊號代表方向錯了，該換路而不是重試

**觸發訊號**（≥ 2 個成立 → 停止重試，進入換路程序）：
- [ ] 每次修完，症狀換一個地方冒出來（打地鼠模式）
- [ ] 修復程式碼越改越特例化（開始出現只為某個 case 存在的 if）
- [ ] 我的解釋需要越來越多「剛好」才成立（「可能是快取剛好…加上時序剛好…」）
- [ ] 我在跟框架/工具對抗，而不是順著它用（文件說 A 用法，我在 hack 出 B）
- [ ] 驗收條件被我不知不覺改寫過了（從「數字正確」滑成「數字看起來合理」）
- [ ] 同一症狀第 3 次（決策表表 2 硬熔斷）

**換路程序**：(1) 停手；(2) 列出目前路線的**全部前提假設**，逐條到真相來源（決策表表 4）驗證；(3) 找出第一個被推翻的假設；(4) 從該假設分岔處提出替代路線，帶代價比較；(5) 替代路線若動到既有功能/範圍 → 按判準 3 問。

- **正例**: PM-010——statusLine 設定三次「應該生效了」都沒生效，第三次停手改用 `--debug` 實測，發現設定被靜默丟棄，**換 JSONL 主軌**根治。換路，不是第四次重試。
- **反例**: PM-011——cost 顯示錯誤，三次都在「修最後看到症狀的那一行」，沒有回頭驗「app 跑的到底是不是新 build」這個前提，燒 20 天。

## 判準 5：品質底線怎麼驗

「品質」不可驗；「底線清單」可驗。按產物類型查：

| 產物 | 底線清單（全過才算過） |
|------|---------------------|
| 程式碼 | 決策表表 1 對級證據＋lint 0 errors＋typecheck exit 0＋基準線測試全綠（紅 = 你弄壞了，決策表表 5） |
| 功能交付 | 上行 ＋ `quality-checklist.md` 對應 Gate 條目 ＋ 實際操作過該功能（不是只跑測試） |
| UI | 上行 ＋ `design-system.md` 的 token（不得出現 hardcode 顏色/間距） |
| 制度/規範文件 | **弱模型可執行性三問**（見下）＋ read-back 驗收（`model-dispatch.md` 第 7 節） |
| 對外文字（報告、文案） | 無事實錯誤（每個數字有來源）＋無編造引用 ＋ 語氣品味屬模糊題：出候選問使用者，不自行定稿 |

**弱模型可執行性三問**（寫任何規則前自問）：
1. 一個 Sonnet 在沒有本 session context 的情況下，讀了這條規則知道**什麼時候**適用嗎？（有可觀察觸發訊號嗎）
2. 知道**具體做什麼**嗎？（有指令/步驟，還是只有形容詞）
3. 知道**做到什麼程度算完**嗎？（有驗收標準嗎）

- **正例**: 「宣告完成前跑 `node scripts/preflight.cjs`，貼輸出」——觸發、動作、驗收三者俱全。
- **反例**: 「保持高品質、謹慎行事」——三問全掛，等於沒寫。發現制度文件裡有這種句子，按 `maintenance-protocol.md` 提案改寫。
