# 模型調度守則 — 指揮官不下場

> **版本**: v1.0（2026-07-06，Fable 5 制度建設 session）
> **讀者**: 主對話的模型（任何等級）。規則寫到 Sonnet 等級可直接執行。
> **適用範圍**: Claude Code 的 subagent 調度（`Agent` 工具）。AgentHub 公司層的 Agent 委派（SendMessage 給 studio-producer 等）另見 `.knowledge/team-workflow.md`，本文件不覆蓋。
> **配套**: 派工時直接抄 `delegation-templates.md` 的模板；拿不準要不要升級時查 `judgment-rubrics.md` 判準 1。

---

## 1. 指揮官不下場（第一原則）

主對話（指揮官）的 context 是全 session 最貴的資源（原因見 `diagnosis.md` 漏 1）。

**必須派 subagent、禁止自己做**：

| 動作 | 判定門檻（達到就派） |
|------|-------------------|
| 大量讀取 | 需要讀 > 3 個檔案才能下結論；或單檔 > 400 行（不知道行數就先 `wc -l`，1 秒）而你只需要其中的結論 |
| 掃 repo / 找東西 | **派工前自問：一個精確字串的單次 Grep 解得了嗎？解得了 → 自己做，不派。** 第一次 Grep 沒找齊、需要換關鍵字重試 → 停手改派 Explore |
| 查網頁 / 外部研究 | 任何 WebSearch / WebFetch 超過 1 次往返的研究 |
| 批次改檔 | 同一模式要套用到 > 3 個檔案 |
| 長輸出指令 | 預期輸出 > 200 行的測試 / build / log 分析 |

**指揮官自己做、不派**：

- 讀單一已知檔案的已知段落（用 `offset`/`limit` 只讀需要的部分）
- 一個精確字串的單次 Grep（廉價動作；要換第二個關鍵字時就該派了）
- 單檔的精準 Edit
- 所有「決定」：方案取捨、驗收判定、與使用者溝通
- 派工 prompt 的撰寫與 subagent 回報的整合

**岔出的新需求**：做 A 途中發現該做 B → B 一律先寫進 backlog（`.tasks/` 或任務清單），不當場做。例外：B 是 A 的阻塞前置（不做 B 則 A 無法驗收）。

## 2. 本環境實際可用的調度資源（實查於 2026-07-06，不要憑印象）

### Subagent 類型（`Agent` 工具的 `subagent_type`）

| 類型 | 能力 | 用途 |
|------|------|------|
| `Explore` | 唯讀（不能 Edit/Write） | 掃 repo、找檔案、盤點結構。只回結論不回檔案傾印 |
| `Plan` | 唯讀，架構師 | 設計實作方案、權衡取捨 |
| `general-purpose` | 全工具 | 實作、重構、批次改檔、研究 |
| `claude-code-guide` | 唯讀＋Web | 查 Claude Code / Agent SDK / Claude API 的用法問題 |
| `fork` | 繼承主對話全部 context，同模型 | 需要完整上下文的分支任務；**不能**用 `model` 降級 |
| （AgentHub 專案自訂） | 見 `agents/definitions/` | 公司層角色，經 AgentHub app 的 Session 機制運作 |

### 模型（`Agent` 工具的 `model` 參數）

| 值 | 定位 | 相對成本（粗估） |
|----|------|----------------|
| `haiku` | 機械執行層：已解模式批次套用、格式轉換、簡單查找 | 1× |
| `sonnet` | 主力執行層：搜尋、實作、重構、常規研究 | ~4× |
| `opus` | 判斷層：設計、難題除錯、高風險審查、第二意見 | ~20× |
| `fable` | **不列入常規調度**（一次性配額，已於 2026-07-06 用畢） | — |

**派工時一律顯式指定 `model`，不依賴預設**（預設值因 agent 類型而異，依賴它 = 猜）。

### Effort（誠實標註）

本環境**目前無法**在單次 `Agent` 呼叫中指定 reasoning effort——effort 由 agent 定義檔（`.claude/agents/*.md` frontmatter）決定，而本專案目前**沒有** `.claude/agents/` 目錄（實查 2026-07-06）。若未來需要 effort 控制：建立自訂 agent 定義檔（先查 `maintenance-protocol.md` 權限分級——這屬「先問老闆」級）。

## 3. 派工三件套（缺一不派）

每個派工 prompt 必須含以下三段。**驗收條件空著 = 不准派**（`diagnosis.md` 焦 3 的直接對策）：

1. **目標與動機** — 要做什麼＋為什麼（subagent 知道動機才能在細節上做對取捨）
2. **驗收條件** — 可機械檢查的完成定義（指令跑得出什麼、檔案裡有什麼、哪些情況算失敗）
3. **回報格式** — 按第 5 節回報合約，模板見 `delegation-templates.md`

另外必附：**環境提示段**（Windows 陷阱 3 行，模板已內建——subagent 讀得到 CLAUDE.md，但關鍵陷阱要在 prompt 裡再說一次，防止它沒讀）。

## 4. 任務 → 類型與模型 對照表

| 任務型態 | subagent_type | model |
|---------|--------------|-------|
| 找檔案 / 掃結構 / 「X 在哪裡」 | `Explore` | `sonnet` |
| 已解模式批次套用（重命名、格式修正、抄模板改參數） | `general-purpose` | `haiku` |
| 實作新功能 / 修 bug / 重構 | `general-purpose` | `sonnet` |
| 外部研究 / 文件查證 | `general-purpose` | `sonnet` |
| 設計方案 / 架構取捨 | `Plan` | `opus` |
| 高風險審查 / 第二意見 / 除錯升級後 | `general-purpose` | `opus` |
| 驗收（read-back / 跑測試） | `general-purpose` | `sonnet`（fresh context，見第 6 節） |

## 5. 回報合約（寫進每個派工 prompt）

subagent 只准回：

1. **結論**（≤ 10 行）＋關鍵證據的 `檔案:行號`
2. **長產物一律落檔**，回傳檔案路徑，不貼全文
3. **實際執行過的驗證指令＋輸出摘要**（≤ 5 行）
4. **「未驗證」清單** — 沒驗過的就標未驗證，禁止把推論寫成事實（決策表核心規則 1 對 subagent 同樣生效）

指揮官收到回報後：只把結論納入主對話；需要細節時針對性地讀它指出的 `檔案:行號`，不重做它的工作。

## 6. 升降級路徑（能力熔斷，補足決策表表 2 的除錯熔斷）

「錯一次」的定義：驗收條件未達成，或回報內容經抽查與事實不符。

| 情況 | 動作 |
|------|------|
| `haiku` 錯 1 次 | **直接升 `sonnet`**，不給第二次（便宜模型重試比升級更貴——重試燒指揮官的整合成本） |
| `sonnet` 同一子任務連錯 2 次 | 升 `opus`，且 prompt 必須帶**完整失敗軌跡**：兩次各試了什麼、錯誤輸出原文、目前的假設清單 |
| `opus` 同一子任務連錯 2 次 | **停**。查 `judgment-rubrics.md`：判準 4（是不是方向錯了該換路）→ 判準 3（要不要問老闆）。禁止第三輪 |
| 難題被 `opus` 解出、同模式還要套 N 處 | **降回 `haiku`/`sonnet` 批次套用**，把解出的模式寫成明確步驟放進派工 prompt |
| 同一件事（同一驗收條件） | 每個模型層級最多 2 輪；整件事在任何情況下**總計不超過 2 次升級**，到頂就停 |

升級時**換 fresh subagent**，不在原 subagent 上繼續（失敗的 context 會污染重試；失敗軌跡由指揮官摘要後帶入，不是整段轉貼）。

## 7. 驗證不自驗

做的人不能自己宣告通過。驗收一律派 **fresh-context** agent（不知道實作過程、只拿驗收條件）：

| 產物 | 驗法 |
|------|------|
| 文件 / 制度檔案 | read-back：驗收 agent 讀檔，逐條回答「驗收條件 X 在檔案哪一行被滿足」 |
| 程式碼 | 跑測試或實跑（`node scripts/preflight.cjs`＋相關 vitest），證據等級查決策表表 1 |
| 高風險判斷（會刪東西、動制度、動 production） | 加第二意見：獨立 `opus` agent 在**看不到第一份答案**的情況下重答，比對分歧；或生成 2-3 份答案派評審 agent 選優並說明理由 |

**誠實條款（harness 的極限）**：拆解、驗證、多樣本評審補得了執行品質；**模糊題與品味判斷補不了**（「這個 UI 好不好看」「這段文案得不得體」「兩個都對時選哪個」）。遇到時按序：(a) 升 `opus` 出候選＋理由 → (b) 仍拿不準就帶選項問老闆（見 `judgment-rubrics.md` 判準 3）→ (c) 明說「這超出我能可靠判斷的範圍」。禁止假裝有把握。
