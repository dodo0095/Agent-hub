# Sprint 提案書: Sprint 6 — 封存專案隔離（Archived Projects Isolation）

> **提案人**: product-manager
> **日期**: 2026-05-08
> **專案**: AgentHub
> **狀態**: ✅ G0 通過（2026-05-08，老闆口頭核准「通過」，未對 5 條建議提出調整 → 全數依建議定案）

---

## 1. 背景

### 老闆原話

> 「幫我排一個工作近 sprint 就是 專案可以關閉跟刪除 不要只有封存 我好多搞錯的專案 不能刪除」

### 痛點根因（PM 診斷後修正）

老闆原訴求是「補刪除/關閉功能」，但經過代碼調查 + 對話釐清，**真實痛點不在資料留存**，而在：

1. **「搞錯的測試專案」會在啟動工作時干擾選擇** — Session Launcher、任務選擇器、Sprint 建立流程的下拉選單裡都還看得到
2. **封存按鈕一次只能處理一個專案** — 老闆有「好多」搞錯的專案，逐個點封存太累
3. **誤封存後無法回復** — `archived` 狀態在 `ProjectDetailView.vue:267` 是終態，沒有 unarchive 按鈕

### 老闆已決策（2026-05-08 G0 前對話）

四個核心問題收斂為「**全部用封存**」：

| 議題 | 老闆裁示 |
|------|---------|
| 「關閉」是否等同「封存」 | 用封存即可 |
| 刪除按下去清到什麼程度 | 不要刪除，用封存 |
| 二次確認嚴格度 | 不需要刪除流程，用封存 |
| **核心要求** | **「啟動工作的時候，不要讓我能選擇封存的專案」** |

→ 本 Sprint **不做 delete 功能**，專注於「讓封存的隔離效果真的有效」。

### 系統現況關鍵發現

| 項目 | 現況 | 影響 |
|------|------|------|
| `PROJECT_DELETE` IPC | 後端已實作，UI 無入口 | 本 Sprint 不啟用，繼續隱藏 |
| `archive` 行為 | 只改 DB `status='archived'`，檔案保留 | 維持現狀，符合老闆需求 |
| 封存專案在工作選單 | **仍然顯示**（無過濾） | 本 Sprint 主要修復目標 |
| 解除封存 | 無此功能 | 本 Sprint 補上（避免誤封死局） |

---

## 2. 目標

讓「封存」真正成為**將專案從日常工作流隔離**的動作，老闆封存後就不再看到、不再選到、不會誤觸；同時提供安全的「批次處理」與「誤封還原」雙保險。

| 工作流程 | 現況 | 目標 |
|---------|------|------|
| Session 啟動選擇專案 | 已封存的專案仍出現在下拉選單 | 預設過濾，需明確切換才會出現 |
| 任務選擇器 | 已封存專案的任務仍可選 | 已封存專案的任務不可選/不顯示 |
| 專案列表頁 | 已封存與進行中混在一起（只是顏色不同） | 預設摺疊已封存，提供「顯示已封存」開關 |
| 一次處理多個搞錯的專案 | 必須逐個進入詳情頁點封存 | 列表頁支援多選 → 批次封存 |
| 誤封後想恢復 | 不可能（archived 是終態） | 提供「解除封存」回到 `paused` 狀態 |

## 3. 範圍定義

### 做

| # | 功能/任務 | 優先級 | 說明 |
|---|----------|--------|------|
| 1 | 全域過濾：所有「啟動工作」選擇器排除 archived 專案 | P0 | SessionLauncher、SessionTaskSelector、Sprint 建立、派工選擇 |
| 2 | 專案列表頁加「顯示已封存」開關（預設關閉） | P0 | ProjectsView，封存區段預設摺疊 |
| 3 | 批次選取 + 批次封存 | P0 | ProjectCard 加 checkbox，列表頁顯示「批次封存（N）」按鈕 |
| 4 | 解除封存（Unarchive）功能 | P0 | archived 專案詳情頁加按鈕，回到 `paused` 狀態 |
| 5 | 過濾 API：`projects.list({ excludeArchived: true })` | P0 | 後端支援，避免前端過濾後仍透過 IPC 傳全量資料 |
| 6 | 已封存專案的 Session、Task、Gate 連動處理 | P1 | 不刪除歷史，但在任務看板、Gate 視圖也預設過濾 |
| 7 | i18n 字串補齊（zh-TW + en） | P1 | 「批次封存」「顯示已封存」「解除封存」等新字串 |

### 不做（明確排除）

- **不做 delete 功能**：老闆明確選擇全部用封存，不要硬刪
- **不做「關閉」狀態**：保留兩段式（active/paused/completed → archived），不新增中間態
- **不動 `PROJECT_DELETE` IPC**：後端 handler 維持現狀（不啟用、不刪除），未來真要做時再啟動 Sprint
- **不做封存資料的清理 / 壓縮 / 匯出**：磁碟上的 workDir 一律保留
- **不改 `archive` 的後端行為**：仍然只改 status，不搬檔案、不停 watcher
- **不做「自動封存」邏輯**（如「30 天無活動自動封存」）：純手動觸發

## 6. 風險評估

| 風險 | 可能性 | 影響 | 緩解措施 |
|------|--------|------|---------|
| 過濾遺漏某個入口（如未來新增的選擇器） | 中 | 中 | 1) 在 `useIpc.ts` 新增 `useActiveProjects()` composable，所有「啟動工作」選擇器強制走它；2) ESLint rule 警告直接呼叫 `projects.list()` 不加參數的地方 |
| 老闆批次選取時誤封一票活躍專案 | 中 | 高 | 1) 批次封存前彈窗列出所有將被封存的專案名稱；2) 批次操作後 toast 顯示「N 個專案已封存，可從列表頁『顯示已封存』還原」 |
| 解除封存後狀態回到 `paused` 但老闆預期是 `active` | 低 | 低 | 統一回 `paused`，由老闆手動 activate；操作說明寫清楚 |
| 後端 list 加參數破壞既有 caller | 中 | 中 | 參數預設 `excludeArchived: false`（向後相容），只在新呼叫處顯式傳 `true` |
| 已封存專案的 Session 已開啟還在跑 | 低 | 中 | 不強制關閉既有 Session（避免破壞工作中），只在新建時阻擋 |

## 7. 失敗模式分析

| 失敗場景 | 可能性 | 影響 | 偵測方式 | 緩解措施 |
|---------|--------|------|---------|---------|
| 過濾邏輯只在前端做，後端仍回傳全量資料 | 中 | 低（不漏資安，只是效能） | Code Review | 後端 `excludeArchived` 為主要過濾，前端為防呆第二層 |
| 批次封存執行到一半失敗（部分成功） | 低 | 中 | 後端 transaction 失敗會吞錯誤 | 1) 後端 batch 用 transaction，要嘛全成功要嘛全 rollback；2) 失敗時前端 toast 列出哪些成功哪些失敗 |
| 「顯示已封存」開關狀態未持久化，每次開頁都要重點 | 中 | 低 | 老闆抱怨 | 用 localStorage 記住偏好 |
| Unarchive 之後 Session/Task 看不到歷史紀錄 | 低 | 中 | E2E 測試 | 確保 unarchive 只改 status，不動底下的 sessions/tasks/gates |

## 8. 可觀測性

- **日誌策略**:
  - `archive(projectId)` / `unarchive(projectId)` / `batchArchive(ids[])` 都要寫 audit log（誰、何時、影響哪些 ID）
  - 過濾掉 archived 的查詢加 `[FilterArchived]` tag
- **關鍵 Dashboard**: 不新增（內部工具，無需監控面板）
- **告警規則**: 批次封存超過 10 個專案時，後端 log 寫 `WARN` 級別（潛在誤觸）

## 9. Rollback 計畫

| 項目 | 說明 |
|------|------|
| 程式碼回滾 | `git revert` Sprint 6 合併 commit；無 DB schema 變更 |
| DB 回滾 | 不適用（無 migration） |
| 判斷標準 | 1) 啟動工作流程因過濾異常而完全卡死；2) 批次封存 bug 導致活躍專案被誤封且無法 unarchive |
| 負責人 | tech-lead 執行 revert，product-manager 通知老闆 |
| 安全網 | 即使前端完全失效，老闆仍可手動編輯 SQLite 把 status 改回 active（postmortem 寫操作步驟） |
